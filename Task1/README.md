# 1. Проблемы текущей интеграции

Наблюдения из учебного кейса отделены от предполагаемых причин. Статусы Closed/Resolved у обращений не доказывают устранения системного дефекта. Задачи и эпики показывают потребность, а не готовую функциональность.

| Проблема | Признаки | Влияние на приложение |
|---|---|---|
| P01. Неопределённый результат платежа и повторное списание | INT-001: списание без фиксации статуса при timeout; SD-004: ожидание 10 с и ошибка; SD-009: два списания | Повторная попытка может повторно снять деньги; нужен журнал paymentIntent, сверка и идемпотентный PSP-контракт, а не слепой retry |
| P02. Дубли записей и конкуренция за слот | INT-005, SD-003: повторный POST/двойное нажатие создают дубли | Два визита на один слот, конфликт пользователей; Idempotency-Key плюс атомарная уникальность слота нужны независимо друг от друга |
| P03. Нет согласованного распределённого процесса | SD-002: после оплаты Booking not found для paymentID; в описании 3.2 нет механизмов отката цепочки | Оплата без записи и незавершённые лабораторные резервы; требуется durable Saga с корреляцией и компенсациями |
| P04. Перегрузка и зависания 1С | INT-003: 503 при >50 RPS; SD-001: >30 с и ручной перезапуск | Блокировка потоков, каскадные ошибки записи; изоляция вызовов, read model полисов, circuit breaker |
| P05. Ошибка зависимости превращается в неверное бизнес-решение | SD-008: null трактуется как недействительный полис, через 5 мин успех | Пациенту ошибочно отказывают в ДМС; нужны отдельные VALID/INVALID/UNKNOWN, свежесть и безопасный fallback |
| P06. Ненадёжная доставка из LIS | INT-002: FTP 425, до 2 ч задержки; SD-005: FTP timeout, REST не повторил передачу, ручной запуск | Анализы недоступны, растут звонки; требуются контроль захвата, durable spool, повторная доставка и сверка |
| P07. Нет защиты от дублей результатов | INT-008: повтор XML даёт дубль в CRM | Разные версии/повторные анализы путают пациента и врача; dedup по resultId/version, контроль patient binding |
| P08. Не контролируется завершение обработки в CRM | INT-011: LIS передала, CRM не обновила, очередь застряла | Транспортная доставка не означает видимость результата; ack только после commit, метрики возраста и сверка read model |
| P09. Переполнение уведомлений и неизвестная ёмкость | SD-006: RabbitMQ переполнена, нет Android push; INT-004 — задача документировать лимиты | Нельзя полагаться на push как единственное подтверждение; нужны backlog alarm, квоты, отдельные очереди и экран состояния в приложении |
| P10. Риск доступа к чужим данным | SD-007: врач видит чужого пациента; подмена сессии лишь гипотеза | Утечка медицинских данных при повторном использовании модели доступа; обязательны проверка владельца ресурса и раздельные роли пациента/сотрудника |
| P11. Инъекция в поиске | INT-006: SQL-инъекция веб-портала | Новый канал не должен повторить уязвимый запрос; параметризованный SQL, валидация, ограничения DB-прав и security regression tests |
| P12. Низкая диагностируемость интеграций | INT-007: нет distributed tracing | Долгое восстановление цепочки оплаты/записи; нужны traceId/operationId и аудит переходов без медицинских payload в логах |
| P13. Возможное узкое место БД расписания | INT-009 — задача репликации из-за блокировок; фактический план запросов не дан | Масштабирование Java-инстансов может не увеличить пропускную способность; замерить lock waits, оптимизировать транзакции, отделить чтение |
| P14. Нет готовой защиты нового входного API | INT-010 — эпик Gateway/rate limiting/idempotency; существующие системы разнородны | Без нового фасада приложение наследует протоколы и отказы legacy, публичные запросы перегружают backend |

Блокеры пилота: P01–P03 и P10–P11. Затем P04–P09 и P12–P14 устраняются до расширения на годовую нагрузку. Новая архитектура и привязка интеграций — [Task2](../Task2/README.md).

# 4.2. Горизонтальное масштабирование

Выбраны Расписание и CRM: самозапись непосредственно нагружает первое, а чтение карточек/анализов каждым мобильным пользователем — вторую. По Расписанию есть признаки конкуренции БД INT-009 и дублей INT-005; по CRM — несвежих результатов INT-011. Масштабирование сервиса без защиты его БД переносит узкое место, поэтому способы ниже включают данные.

| ИТ-система | Реализация горизонтального масштабирования | Ключевое ограничение | Решение для ограничения |
|---|---|---|---|
| Расписание | Stateless Java-реплики за балансировщиком, минимум 3 в разных зонах; autoscaling по CPU, p95 очереди запросов и saturation, ограниченный connection pool. Чтение каталогов/слотов из реплик PostgreSQL и cache с коротким TTL; запись/hold только в primary владельца doctor-slot. При росте записи шардирование по clinicId с фиксированным владельцем слота | Единый writer и конкуренция за популярный слот не устраняются добавлением реплик приложения | Короткая транзакция с уникальным ограничением/условным захватом и idempotency. Поэтапное разделение writer по клиникам, ключ doctor-slot содержит clinicId; move клиники только через остановку её новых команд, перенос, сверку и смену fencing epoch. На реплике показана доступность ориентировочно, окончательный конфликт решает writer |
| CRM | Stateless Java REST-реплики; отдельный consumer pool результатов и ограниченный pool БД. Read replicas/read projection для мобильных запросов; разбиение данных по patientId при достижении write-предела, отдельное объектное хранилище больших результатов при наличии таких вложений | Асинхронная реплика/проекция отстаёт и может вернуть старый анализ или не увидеть только что созданную запись | Возвращать version/updatedAt, мониторить lag. Для чтения после изменения принимать минимальную version и маршрутизировать к owner writer либо вернуть честный pending; не делать безусловный fallback всех читателей на перегруженный primary. Уведомление о результате выпускается после commit, чтение проверяет указанную version |

PostgreSQL-репликация — не multi-master: несколько БД не могут независимо подтвердить один слот. Смена primary требует fencing старого writer, проверки RPO и durable idempotency журнала. Финансовые и подтверждённые резервы требуют согласованного RPO=0 в рамках заявленной отказной модели (например, синхронная реплика в другой зоне); потеря обеих копий остаётся отдельным DR-риском, проверяемым восстановлением из backup и PSP reconciliation.

## Остальные компоненты и границы годовой цели

Gateway/BFF, Saga-workers, Полис-фасад, LIS Integration и Lab Reservation горизонтальны по stateless-вызовам/шардам с lease, inbox/outbox и фиксированным владельцем бизнес-ключа. RabbitMQ — quorum queues, несколько consumer-реплик, раздельные очереди платежей/анализов/маркетинга, нагрузка распределяется по очередям, а не бесконечным ростом одной очереди. IdP и его БД разворачиваются отказоустойчиво, проверка JWT использует локальный cache JWKS. Расширение 1С и LIS требует обследования и поддержки вендора; фасады и read models позволяют масштабировать внешний доступ, но не доказывают горизонтальное масштабирование самого legacy. Для внешнего PSP/провайдеров нужны договорённые квоты и резервирование: собственными репликами нельзя увеличить их мощность. Годовая цель «все компоненты» остаётся gate до измерения и устранения этих ограничений, а не объявляется выполненной схемой.

## Проверка производительности и SLO

500/50 000 пользователей — конкурентные сессии, не RPS. Для расчётного сценария принять **гипотезу**: один запрос раз в 10 с на пользователя, т.е. 50/5000 RPS, и профиль 70% поиск/слоты, 20% записи/результаты, 5% создание записи, 5% статусы операции. Проверить также think time 5 с (100/10 000 RPS), всплеск двойных POST, один популярный слот и долю активных сессий; согласовать профиль по телеметрии пилота. 50k пользователей не оправдывают 50k обращений в 1С/с: quota/async защищают зависимость, но при нехватке свежего покрытия вырастет pending, что отдельно отражается в бизнес-SLI.

Количество реплик `ceil(targetRPS / safeRPSPerReplica)` плюс резерв на потерю зоны. safeRPS определяется тестом при соблюдении P99, CPU <70%, bounded DB connections и очереди; измеренного числа нет. Не задаём выдуманное число серверов для 50k.

В пилоте: 500 VU, 1 час устойчивой нагрузки и 15 мин ×2 burst; перед годовым выпуском: 50k VU на согласованном профиле, 4 часа steady state, 30 мин burst и отключение одного инстанса/зоны. Для каждого типа API измеряются error rate и P99 от клиента; критерии коротких запросов — P99 <1 с и успешность ≥99.95% за согласованное окно. Командный 202 считается успехом только принятия, а доля COMPLETED/возвратов и время Saga отдельно контролируются; нельзя скрыть плохую бизнес-доступность быстрыми 202. Длинный внешний hosted payment измеряется отдельным journey SLI. Профиль, исключения и окно SLO утверждаются до теста, 99.95% не доказывается одним часовым прогоном.

Проверить также kill consumer между commit/ack, остановку 1С/PSP, восстановление очереди, повтор после failover и сверку слотов/денег/анализов. Регулярный restore drill проверяет backup; метрики lock waits, replication lag, oldest message age, error budget и UNKNOWN payments входят в release gate. Это план приёмки архитектуры; реальных нагрузочных тестов в проекте нет.

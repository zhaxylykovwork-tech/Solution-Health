## Цели и этапы

| Горизонт | Цель из кейса | Решение и проверка достижения |
|---|---|---|
| 3 месяца, MVP | Запись, оплата, уведомления; 500 одновременных пользователей; на 30% меньше нагрузки кол-центра | API Gateway, надёжная запись/Saga, платёжная сверка, доставка уведомлений. Прогон 500 виртуальных пользователей с согласованным профилем; сравнить обращения по записи на 1000 визитов до/после запуска, учесть сезонность и контрольные клиники |
| 12 месяцев | 70% визитов через онлайн-запись, рост среднего чека за счёт дополнительных услуг | Анализы и ДМС в приложении, лабораторные резервы, предложения дополнительных услуг с отдельным согласием. Онлайн-записи / все записи с дедупликацией; средний чек сравнивается при сопоставимом составе пациентов и услуг |
| 12 месяцев | До 50 000 одновременных пользователей, <1 секунды для 99% запросов, 99.95% доступности | Короткие API-запросы, асинхронные длительные операции, горизонтальные реплики, read models, изоляция legacy. Проверка по [плану нагрузки](Task4.2/README.md); принятие запроса за <1 с не означает завершение оплаты за <1 с |

Первые 4 недели: устранить SQL-инъекцию и нарушения доступа, согласовать контракты PSP/1С/LIS, внедрить уникальность записи, Idempotency-Key и наблюдаемость. Недели 5–8: Gateway, Saga, адаптеры, надёжные очереди, политика ДМС. Недели 9–12: fault/load/security-тесты, сверка платежей, пилот одной клиники с feature flags и постепенное расширение. Месяцы 4–12: результаты анализов и лабораторные резервы, масштабирование read-контура, отказоустойчивые кластеры и тренировки восстановления. Откат пилота переключает канал записи на старый интерфейс; уже начатые Saga доводятся до терминального состояния, их платежи не повторяются.

## Границы достоверности и допущения

Из кейса известны Java/REST/PostgreSQL у Расписания и CRM, SOAP/FTP/REST у LIS, HTTP-шлюз 1С и синхронный REST внешнего PSP, RabbitMQ у уведомлений. Известны сбои 1С выше 50 RPS и ожидание до 30 секунд. Остальные численные значения ниже — стартовые проектные настройки, требующие замеров.

Не заданы профиль запросов, размеры анализов, сроки хранения, мощности, бюджет, окна SLO, контракты возврата/статуса PSP и способ получения изменений 1С/LIS. Это входы для технического обследования, а не выдуманные факты. Новый Lab Reservation ведёт собственный календарь квот забора биоматериала: наличие write API у существующей LIS не предполагается. До запуска клиника должна утвердить владельца календаря, импорт квот и отключение параллельной несогласованной записи на те же квоты.

99.95% предлагается измерять за 30 дней: бюджет недоступности `30 × 24 × 60 × 0.0005 = 21.6 минуты`. Границы клиентского пути и исключения согласуются до пилота. Для P99 <1 с целевой бюджет короткого API: сеть/edge 150 мс + auth/routing 100 мс + сервис 350 мс + БД/read model 150 мс + резерв 250 мс = 1000 мс (строго <1000 мс проверяется на тестах; бюджет — верхние ориентиры, не сложение измеренных перцентилей). Медленная внешняя операция возвращает 202 с operationId и продолжается асинхронно; пользователь видит реальный статус.

## Первичные технические источники

Проверены 08.11.2026: [OpenAPI 3.0.3](https://spec.openapis.org/oas/v3.0.3.html), [OpenAPI 3.2.0](https://spec.openapis.org/oas/v3.2.0.html), [OAuth для native apps, RFC 8252](https://www.rfc-editor.org/rfc/rfc8252), [RabbitMQ confirms и acknowledgements](https://www.rabbitmq.com/docs/confirms). Они подтверждают формат контракта, использование внешнего браузера для native OAuth и разделение publisher confirms/consumer ack. Настройки, архитектурные границы и эксплуатационные критерии в проекте предложены автором решения.
